The shift that changes everything

Stop thinking about who writes the code. Start thinking about who owns what. The product person owns the brief, the customer, and the design. The developer owns the foundations, the safety, and the architecture. AI handles the translation between the two. Once you divide the roles this clearly, everything accelerates.

02 · The Builder's mindset

How the Builder thinks

The mistakes I made when I started weren't technical. They were about how I was thinking about the work. Here's what changed.

01

The prompt is the new spec

Your job isn't to write code. It's to write the brief. Structure every prompt like a spec: what you're building, who it's for, what it should do, what it should look like, what states to handle, and what the constraints are. If you can't explain it clearly, the AI won't build it correctly.

02

Plan first, always

AI doesn't plan ahead unless you do. If you just say "build this," it starts at the top and skips everything else. Prompt to get the structure first, make edits, then implement. Every time I skipped this step, I paid for it later.

03

Build every feature with five states

Default, Loading, Success, Error, Empty. If you only build the success state, you've built half a feature. The other half is what the user sees when something goes wrong — and they always notice.

Every feature. Every time. Default · Loading · Success · Error · Empty
04

When everything collapses, stop

Don't keep prompting into a broken context. Stop. Describe the problem as a user — not as a developer. Get AI feedback on why it's stuck. Start fresh from the plan. This is almost always faster than pushing through.

05

Build once, replicate five times

Every pattern you build — an auth flow, a file upload, a multi-tenant structure — can be replicated. Turn your patterns into reusable prompts. What took two days the first time takes two hours the fifth time.

06

Test like a user, not a builder

Log in. Log out. Go through the whole flow on mobile. Pretend it's your first time. Then try to break it — refresh mid-form, submit strange data, navigate away early. If it handles all of that, you're done.

03 · The prompt formula

Structure every prompt like a brief

If you can't explain it clearly, the AI won't build it correctly. These six elements work at the beginning of a project and at the feature level as you go.

WHAT
What you're building
e.g. "A recipient selection screen"
WHO
Who it's for
e.g. "A lawyer under time pressure at 10pm"
PURPOSE
What it should do
e.g. "Fast validation, not a complete form"
DESIGN
What it should look like
e.g. "Here's a screenshot of the competitor"
STATES
All conditions to handle
e.g. "Loading, empty, error, full"
CONSTRAINTS
Technical limits
e.g. "Must work on mobile, RLS enabled"

06 · The Architect's blueprint

What the Architect builds first

Before the Builder writes a single prompt for a feature, the Architect puts these six foundations in place. Without them, every feature you ship is one bug away from breaking everything else.

01 · Auth

Login, sign-up, forgot password

Use Supabase's built-in auth. Connect it in Cursor by pasting your project URL and key into the environment config. You get sign-up, login, forgot password, and redirect logic out of the box. First-time users go to onboarding. Everyone else goes to their dashboard.

02 · Multi-tenant

One app, many clients

Every record in your database gets a client_id. Admins can switch between clients via a dropdown. Users only see data for their current client. I tested this with mock data first — two fake clients with completely separate records — to catch cross-client bugs early.

03 · Payments & Balances

Track every cent

Build a balances table (user_id, currency, amount) and a transactions table (user_id, amount, currency, recipient_id, timestamp, status). Status starts as pending, moves to completed or failed. When completed, subtract from balance. This becomes the backbone of the product.

04 · File Uploads

Documents, IDs, contracts

Uploads go to Supabase Storage. Each file gets metadata in a documents table: user_id, file_url, type, label, created_at. Users can rename and delete files. All paperwork, secured, organized, in the app.

05 · Security

Row-Level Security

Enable RLS on every table. Users can only read rows where client_id matches theirs. Admins get access to their assigned clients only. Add a role field to users to differentiate. If you handle money or personal data, this is not optional.

06 · Third-party integrations

Edge functions for everything else

Need to send emails, post to Slack, trigger an automation? Use Supabase Edge Functions. Small backend scripts that run on events. Store API keys as environment variables — never expose them in the frontend. This is how I connected to Resend, payment APIs, and more.
